# 上板与验收

## 摄像头和厂商 BSP

先通过正点原子自带相机应用确认排线与镜像，再用 `sh scripts/probe_camera.sh` 查看媒体拓扑。沿 OV13850 subdev 的已启用链接查到 ISP 及 `rkisp_mainpath`。驱动、设备树、电源时序、板级引脚和 IQ 文件属于镜像与 SDK；应使用手头底板版本的配套配置。厂商文档列出了 OV13850 的 MIPI CSI 支持。
[正点原子软件资源说明](https://wiki.alientek.com/docs/Boards/Linux/CLRK3568F/DLRK3568%20%E7%A1%AC%E4%BB%B6%E5%8F%82%E8%80%83%E6%89%8B%E5%86%8C/notice/2.2/)

| 现象 | 怎么定位 |
| --- | --- |
| 拓扑没有 OV13850 | 查看 `tr -d '\000' </proc/device-tree/model` 和 `dmesg \| grep -Ei 'ov13850\|dphy\|rkisp'`。核对底板版本、排线和镜像启用的传感器。 |
| 找到 sensor 但采集超时 | 确认媒体链接启用，检查厂商相机应用是否占用节点。用选中的节点执行下方的独立采集。 |
| 画面黑、偏色 | 用实际 NV12 尺寸和像素格式播放快照。若厂商预览也异常，检查对应 OV13850 的 IQ、3A 进程及曝光。 |
| 模型初始化失败 | 对照板上的 RKNPU 驱动、`librknnrt.so` 和 Toolkit2 的兼容关系，确认模型目标为 `rk3568`。 |
| 盒子整体偏移 | 先用普通 COCO 场景检查。当前框已按两个轴的缩放和 padding 映射回捕获图像，核对模型是否使用示例的三路 post-sigmoid YOLOv5 输出。 |
| 视频花屏或绿边 | 查看 `V4L2 stride` 和 MPP 输入日志。720p 常能直接导入，1080p 的纵向对齐通常触发重排，UV 从真实偏移复制。 |
| RTMP 断线 | 先断网确认本地 H.264 继续生成，再恢复服务。从终端检查 FFmpeg 和重连日志，并在播放器验证后续 IDR 可以正常解码。 |

把命令中的设备替换成探测结果。打开应用前结束这条采集命令。

```bash
node=/dev/video0
v4l2-ctl -d "$node" --set-fmt-video=width=1280,height=720,pixelformat=NV12 \
  --stream-mmap=8 --stream-count=60 --stream-to=/dev/null
```

## Buildroot 交叉编译

在 Linux 编译机上使用对应正点原子镜像的 AArch64 Linux SDK。下面的 `CXX` 填 SDK 内支持 C++17 且 ABI 与目标镜像匹配的编译器。若原厂只给了较老工具链，则用同镜像 libc/ABI 的新版 SDK，或在配套的 Debian/Ubuntu 开发环境原生构建。

```bash
CXX=/absolute/path/to/sdk/bin/aarch64-linux-gnu-g++
SYSROOT=$("$CXX" -print-sysroot)
test -n "$SYSROOT" && test -d "$SYSROOT" || exit 1
cmake -S . -B build-aarch64 -DCMAKE_SYSTEM_NAME=Linux \
  -DCMAKE_SYSTEM_PROCESSOR=aarch64 -DCMAKE_CXX_COMPILER="$CXX" \
  -DCMAKE_SYSROOT="$SYSROOT" -DCMAKE_FIND_ROOT_PATH_MODE_LIBRARY=ONLY \
  -DCMAKE_FIND_ROOT_PATH_MODE_INCLUDE=ONLY -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build-aarch64 -j2
file build-aarch64/inspection_robot
```

将可执行文件与 `config/`、`model/` 一起部署。启用加速功能时把对应库和头文件路径传给 CMake，用板上的 `ldd ./inspection_robot`（若镜像提供）确认加载的是对应的 ARM64 库。

## 从快照到推流的验收顺序

| 阶段 | 通过条件 |
| --- | --- |
| 采集 | 观察 `frames=120`、`measured_fps`、`v4l2_gaps`。快照字节数等于实际宽 × 高 × 1.5，画面布局与颜色正常。 |
| NPU | 确认 `inference_frames` 增长。用示例模型对准有人的场景，在正常光照下查看产生的 NDJSON，确认框在图像范围内。打开 RGA 后检查是否触发 CPU 回退。 |
| MPP | `ffprobe -v error -show_streams inspection.h264` 能读出 H.264 及正确尺寸，播放确认色彩与画面完整。 |
| RTMP | 播放端能解码可读画面，服务短时中断后新会话从带 SPS/PPS 的 IDR 恢复。 |
| 稳定性 | 连续运行 10 分钟，记录三个丢帧计数、过程实际帧率及退出状态。逐项对比单采集、检测、编码和并行运行。 |

2026-11-23，ATK-DLRK3568 上的 `inspection_robot_aarch64` 从 `/dev/video0` 采集了 120 帧 1280×720 NV12。统计显示全程平均 29.56 fps、`v4l2_gaps=0`，保存的 `frame.nv12` 为 1,382,400 字节。快照按工程的 BT.601 全范围转换显示为 1280×720 PNG，室内景物和颜色可辨认，左上角有高光过曝。

[RKNN 上板测试包](../out/ov13850-rknn-test/README.md)的实时检测结果。2026-11-23 在 ATK-DLRK3568 实测通过。应用采集 120 帧 1280×720 NV12，平均采集帧率 29.57 fps，`v4l2_gaps=0`。RKNN 完成 65 帧推理，推理队列替换了 55 帧旧帧。事件日志包含 `tv` 和 `chair` 的类别、置信度和框坐标。

2026-11-23，[MPP 本地录像测试包](../out/ov13850-mpp-test/README.md)在 ATK-DLRK3568 上完成 180 帧 1280×720 NV12 采集与 H.264 编码。运行时从 V4L2 导入 DMA-BUF，平均采集帧率 29.77 fps，`v4l2_gaps=0`，`stream_queue_drops=0`。输出 `inspection.h264` 大小为 1,806,039 字节。原始 H.264 以 30 fps 封装为 6 秒 MP4，确认全部 180 帧均可解码，抽帧画面完整。

2026-11-23，[RKNN 与 MPP 并行测试包](../out/ov13850-combined-test/README.md)在 ATK-DLRK3568 上完成 300 帧 1280×720 NV12 采集、160 帧 RKNN 推理和 300 帧 H.264 编码。平均采集帧率 29.88 fps，`v4l2_gaps=0`、`stream_queue_drops=0`、`inference_queue_drops=140`。生成 3,060,704 字节的录像并输出 `person`、`tv` 检测事件。录像按 30 fps 封装为 10 秒 MP4，全部 300 帧解码成功。日志含 662 条检测结果，所有框坐标均在图像边界内。将首组检测记录叠加到录像首帧作目视对照，可以辨认人物、屏幕和椅子，其中左侧屏幕框偏宽。当前录像没有记录逐帧序号映射。

2026-11-23，ATK-DLRK3568 经 Wi-Fi 热点向 Windows 实时推送 H.264。Windows 接收并完整解码 298 帧 1280×720、30 fps 视频，时长约 9.93 秒。板端报告 2 帧编码队列丢帧和 FLV 时间戳提示。

2026-11-24，Windows RTMP 接收端关闭 6 秒后重新监听，板上程序在同一次运行中恢复推流。Windows 断线前和重连后分别录制约 5 秒，每段 150 帧，均完整解码。

2026-11-24，RGA 与 CPU 对同 3 帧图像分别进行预处理和 RKNN 推理，完成 9 对同类别检测框配对。三帧的配对框 IoU 中位数分别为 0.975、0.917 和 0.969。第 65 帧 CPU 额外输出一条置信度 0.43 的 `mouse` 检测。

2026-11-24，[全功能联测包](../out/ov13850-full-test) 在板上同时运行 RGA、RKNN、MPP 本地录像和 RTMP 推流。采集 900 帧，平均 29.99 fps，`v4l2_gaps=0`，完成 507 帧推理，输出 1,461 条检测记录。编码队列丢弃 3 帧，板端 H.264 与 Windows 接收录像均解码 897 帧。Windows 录像为 1280×720、30 fps，时长 29.90 秒。接收端收尾时有 RTMP I/O 提示，接收脚本记录退出状态为 0，保存的视频完整解码。

本次验收范围为视觉功能。导航和底盘沿用原项目的伪代码。长时间稳定性与开发板断开 Wi‑Fi 的联测未纳入本次验收。

采集队列容量按同时在途的分支持有量验证。检测线程拿到 RGB 后归还 NV12 引用，编码线程取到 H.264 后归还 NV12 引用，最后一个引用释放才执行 `QBUF`。RGA 可导入原帧 DMA-BUF，RKNN 通过 `rknn_inputs_set` 接收 RGB。MPP 对齐满足时直接导入 DMA-BUF，其他情况由编码器的对齐缓冲区接收可见行。H.264 文件和 RTMP 按协商或配置的标称帧率组织，编码队列丢帧时最终媒体时长可能短于采集时长。

### 离线逻辑自测

```bash
cmake -S . -B build-test -DROBOT_BUILD_CAMERA=OFF
cmake --build build-test
(cd build-test && ctest --output-on-failure)
```

该测试覆盖配置、带行 padding 的 NV12、letterbox 坐标还原、YOLOv5 NMS 和有界队列丢旧策略。摄像头、RGA、NPU、MPP 和 RTMP 的实机结果要在目标板记录。
